## Physical design boundary

### `OfflineE2E01Composition`

`bootstrap.py` 新增一个显式构造、无 module-level app/Provider/engine 的装配对象：

1. 只接受 `LoadedE2E01Artifacts`、已有 PostgreSQL `sessionmaker`、UTC clock 与 UUID factory。
2. 对 authenticated `fixture` 再做 exact nested shape/type/cardinality 校验：
   - Session 只接受 `fixture_ref`、`label`、`session_id`、`trusted_customer_id`、`trust_boundary=SERVER_SIDE_FIXTURE_ONLY`；
   - Order 只接受 `fixture_ref`、`owner_customer_id`、`safe_projection`，并 strict 构造 `OrderSummaryProjection`；
   - sentinel 只接受 `fixture_ref`、`order_number`、`seed_behavior=MUST_NOT_INSERT`；
   - refs、raw session IDs、order numbers 唯一，sentinel 与 seeded order 不重叠；
   - versions 只作为现有 Runtime/Tool/Renderer/Redaction 配置输入，不充当业务事实或权限。
3. Session 的 `subject_ref`、`orders:read` scope 与 non-expiring local expiry 都由服务端装配生成；用户消息与 HTTP body不能提供或覆盖。
4. `start()` 先以 `PostgresRestartRecoveryAdapter` + `RestartRecoveryService` 循环处理 closure，直到返回 `closure_found=false`；任何 `ready=false` 或非 `APPLIED` 结果抛出 fresh parameterless bounded startup error。完成后才 seed authenticated fixture 中的真实 orders；sentinel 永不插入。
5. RegistrySnapshot 恰好注册现有 `get_order` READ registration，版本来自 authenticated fixture；不注册 `get_shipment` 或其他工具。

### Per-Case HTTP SUT

1. `OfflineEvalHarness` 传入的 `ScriptedModelProviderV2` 只服务本次 `execute_case`；每次重新构造 `AgentRunService`、`ReadToolExecutor` 与 FastAPI app。
2. 使用 HTTPX `ASGITransport` 对 `POST /v1/agent/runs` 发真实 HTTP 请求，Cookie 来自 server-owned fixture ref；body 只包含本次唯一 user message。
3. handler wrapper只捕获 HTTP authentication 后实际 `AgentRunCommand.customer_context` 导出的 `TrustedOwnerScope`，并在成功结果后绑定到 `run_id`。不得从 fixture customer ID直接构造 evidence owner scope，也不得把 `run_id` 当授权。
4. HTTP response strict decode为 `AgentRunResult`；使用已绑定 owner scope调用 `load_exact_run_evidence_for_owner`，随后只调用 `map_exact_run_http_result_to_sut_result`。不读取 Provider internal cursor、script、Case expectations或 transient RU output。
5. `runtime_fault=None` 是三个目标 Case 的唯一默认路径；如支持现有 stale-state directive，只能把它转换成现有 `ApplyTaskTransitionCommand` + Trace，不得扩展 taxonomy。

### PostgreSQL Trace/Eval bridge

1. `append_eval_case_graded(event)` 根据先前 HTTP handler 已绑定的 `event.run_id` 取得 owner scope，确认真实 Run存在后调用现有 append Trace Port。
2. `reload_trace(trace_ref)` 要求 `trace_ref` 精确等于已绑定的真实 `run_id`，再调用 owner-scoped `list_trace_events_for_owner`。
3. `build_harness()` 复用同一 `PostgresRecordAdapter` 作为 `EvalResultPort`；candidate/runtime versions只来自 authenticated `LoadedE2E01Artifacts`。
4. 不新增 raw SQL、第二个 evidence reader、synthetic closure、fake Trace store或 in-memory EvalResult fallback。
